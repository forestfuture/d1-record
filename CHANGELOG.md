# @forestfuture/d1-record

## 0.1.0

### Minor Changes

- [`724ecaa`](https://github.com/forestfuture/d1-record/commit/724ecaa1c3145ccd9895be05358602e175031192) Thanks [@christopherstyles](https://github.com/christopherstyles)! - Associations are declared as record fields, written once: `posts = hasMany(Post, { dependent: "destroy" })`, `author = belongsTo(User)`, `profile = hasOne(Profile)`, imported from the package. TypeScript infers each accessor's type, and association scopes are typed from their target. **Breaking:** `static associations = this.defineAssociations({...})` and the `declare posts: HasMany<typeof Post>` lines are gone. Move each association into a field, and drop its `declare` line.

- [`ef341cb`](https://github.com/forestfuture/d1-record/commit/ef341cbee95e971b30d2d38158d62de9f42b7563) Thanks [@christopherstyles](https://github.com/christopherstyles)! - Attribute values are cast to their type when they're assigned or given to a bulk write, and in conditions. Only unambiguous values are accepted: `"false"`, `"0"` and `"off"` are `false` for a boolean, `"42"` is `42` for an integer, and an ISO-8601 string is a `Date`. Anything else throws `TypeError`: `"no"` for a boolean, `"12abc"` or `1.7` for an integer, a number for a string, a time without an offset. Before this, `"false"` was saved as `true`, and `"12abc"` was stored in an integer column.

  A condition value that can't be cast matches nothing, so `find("abc")` on an integer key throws `RecordNotFound`. In a condition, a number matches a string attribute as its digits (`7` finds `"7"`), as `find` does for a text key.

  An override that changes an attribute's `type` without giving a `default` now drops the generated default, so the column's own default applies.

- [`551ab97`](https://github.com/forestfuture/d1-record/commit/551ab97c00dd310b7957b3d3cf1c4d32e74a1a03) Thanks [@christopherstyles](https://github.com/christopherstyles)! - Queries start from the Model, as in Rails: `User.find(id)`, `User.where(…)`, `User.create(…)`, `User.active()`, and every other Relation method as a typed static. With no setup they use the Model's binding (`static binding = "DB"`, written on your `ApplicationRecord`'s base class by `d1-record schema`). For a D1 Session, per-request `onQuery`, or tests outside a Worker, `withDatabase(connect(env.DB, { … }), fn)` gives a request its own database. `batch([...])` writes atomically on the current database. `db.model(X)` still works as before.

  Scopes are now declared one static each, as Rails' `scope :active, -> { … }`: `static active = this.scope((q) => q.where({ isActive: true }))`, replacing `static scopes = this.defineScopes({...})`. They inherit like any static.

- [`997f4d3`](https://github.com/forestfuture/d1-record/commit/997f4d3817aa7a188ac30ca9710439420ba45054) Thanks [@christopherstyles](https://github.com/christopherstyles)! - `onQuery` listeners see the bound values of filtered attributes as `"[FILTERED]"`, as Rails' logs do, and so do cast errors. `static filterAttributes` starts with Rails' default list (`passw`, `email`, `secret`, `token`, `_key`, `crypt`, `salt`, `certificate`, `otp`, `ssn`, `cvv`, `cvc`), matched against each attribute's snake_case name, so passwords, tokens, API keys and emails no longer reach your logs. Replace the list on your app's base class: `static override filterAttributes = [...Model.Base.filterAttributes, "iban"]`, or `[]` to filter nothing. D1 still gets the real values.

- [`80156c3`](https://github.com/forestfuture/d1-record/commit/80156c39a3b55018c7907c7042595edeab4524d2) Thanks [@christopherstyles](https://github.com/christopherstyles)! - First release: a Rails-inspired Active Record for Cloudflare Workers and D1. Models with typed attributes, validations, callbacks, associations and change tracking; lazy, composable queries; atomic batches; and read-replica sessions. See the guide at https://docs.forestfuture.dev/d1-record/.

- [`94a52b8`](https://github.com/forestfuture/d1-record/commit/94a52b82a1c9c6e4fd9d3d1d33587b5d251e77ba) Thanks [@christopherstyles](https://github.com/christopherstyles)! - Bulk writes run when called, as in Rails: `await posts.deleteAll()` and `updateAll(…)` resolve to the number of rows (on `none()`, `0` without a query), and `insert`, `insertAll`, `upsert` and `upsertAll` to D1's `meta`. For `db.batch([...])`, use their `to…` forms (`toInsert`, `toUpdateAll`, `toDeleteAll`, …), as records use `toSave()`/`toDestroy()`. **Breaking:** `.run()` is gone. Drop it where a write ran on its own, and use the `to…` form where a write went into a batch.

### Patch Changes

- [`17ab053`](https://github.com/forestfuture/d1-record/commit/17ab053b79c669d5315b2113e724127db80a96e8) Thanks [@christopherstyles](https://github.com/christopherstyles)! - An app-wide query logger: `static override onQuery: QueryListener = (event) => …` on your app's base class sees every statement of every Model, whichever database runs it, after the database's own `onQuery`. Every query event now says which Model it's for (`event.model`). The guide's Connecting page has a new Logging queries section: app-wide, per request with its ID, development only, Workers Logs, and `Server-Timing`. Every `QueryEvent` now has a required `model` field. A listener that throws no longer fails the query: it's logged with `console.error`, and the query's result or error reaches the caller unchanged.

- [`e2a8a61`](https://github.com/forestfuture/d1-record/commit/e2a8a61dc2ed79c5044cd09e284e9fe626210aa5) Thanks [@christopherstyles](https://github.com/christopherstyles)! - The package ships its guide for coding agents, matching its version (`llms-full.txt`), and an agent skill (`SKILL.md`, installable with `npx skills add forestfuture/d1-record` or `npx skills experimental_sync`). The documentation site publishes `llms.txt`, `llms-full.txt` and every page as Markdown.

- [`06a8d32`](https://github.com/forestfuture/d1-record/commit/06a8d32d5fddc1d81f81d922d9368dc82f9ebece) Thanks [@christopherstyles](https://github.com/christopherstyles)! - `d1-record g model` and `g migration` take `--out`, naming the schema file to regenerate, as `d1-record schema` does: in a Drizzle project with its own `src/db/schema/`, `--out src/db/d1-record.ts`.

- [`6dd2acd`](https://github.com/forestfuture/d1-record/commit/6dd2acda1e5095626e94a9416ff62e4f4723df64) Thanks [@christopherstyles](https://github.com/christopherstyles)! - Generators: `d1-record g model Product name:string! user:references` writes a `CREATE TABLE` migration and `src/models/product.ts`, and `d1-record g migration AddSkuToProducts sku:string:unique` writes a migration from its name (`Create…`, `Add…To…`, `Remove…From…`, or empty). Columns take `!` for `NOT NULL`, `=value` for a literal default, and `:unique` or `:index`. Each migration is checked against the existing ones before anything is written, numbered as Wrangler numbers them, and the schema is regenerated afterwards.

- [`61924cd`](https://github.com/forestfuture/d1-record/commit/61924cd84d4ed560aa090103f4948f4ac3e20311) Thanks [@christopherstyles](https://github.com/christopherstyles)! - A Model's `tableName` is inferred from its class name, as Rails does (`User` → `users`, `BlogPost` → `blog_posts`, `Person` → `people`), so most Models no longer declare it. `static tableName` still overrides it.

- [`afb86d5`](https://github.com/forestfuture/d1-record/commit/afb86d54eebb9771f2aef04433295c54eeb777d4) Thanks [@christopherstyles](https://github.com/christopherstyles)! - A name every object inherits (`constructor`, `__proto__`, `toString`, `hasOwnProperty`), from a URL's `?include=` or a JSON key, is `UnknownAttribute` or `UnknownAssociation` from every method that takes a name, like any unknown name. Before, `includes`, `reloadAssociation`, `loaded`, `isLoaded` and the change-tracking methods found JavaScript's own members instead, and threw a `TypeError` or gave a wrong answer. Reading an unknown attribute through a change-tracking method is now `UnknownAttribute` too.

- [`805f11a`](https://github.com/forestfuture/d1-record/commit/805f11a1e9bdc033b393d1c39568233bf7530377) Thanks [@christopherstyles](https://github.com/christopherstyles)! - Whether two queries or records share a database is decided by the database each resolves to when it runs. Inside `withDatabase`, a loaded record's association now merges or ors with a Model's static Relation (`user.posts().merge(Post.published())`), instead of throwing `IncompatibleRelation`. Records autosaved with an owner built from a Model's statics now keep the database they were saved on, as the owner does. A save or destroy whose records are on two databases (a `belongsTo` target built on another `connect()`) is refused before any validation, callback or write, as a batch's is. The error names where each database came from: the request's, a binding's, or a `connect()` database.

- [`62e7d6c`](https://github.com/forestfuture/d1-record/commit/62e7d6c57aadec3d0eb060556ae57c8afcb94874) Thanks [@christopherstyles](https://github.com/christopherstyles)! - `Model.permit(input, ...names)` keeps only the named attributes of untrusted input (a JSON body, `FormData` or `URLSearchParams`), as Rails' `params.permit`, and casts each value as assigning it would: `User.create(User.permit(await request.json(), "email", "name"))`. A new guide page, Handle untrusted input, covers choosing fields, schema validators, casting, and an untrusted `null` in conditions.

- [`3c979d4`](https://github.com/forestfuture/d1-record/commit/3c979d425d785e54763eeb0e9925ee4f9b95c496) Thanks [@christopherstyles](https://github.com/christopherstyles)! - `d1-record g migration Remove…From<Table>` removes a `references` column like any other, dropping its index and then the column: D1 allows it, so it's no longer refused.

- [`8a0911f`](https://github.com/forestfuture/d1-record/commit/8a0911fcd8710305441fbe6ab1f7d07b602cf7f0) Thanks [@christopherstyles](https://github.com/christopherstyles)! - `d1-record schema` never replaces a file it didn't write, and never writes `src/db/schema.ts` beside a `src/db/schema/` folder (a common Drizzle layout), whose imports it would take over. Either is an error suggesting `--out src/db/d1-record.ts`; the generators check it before writing anything.

- [`9f648b9`](https://github.com/forestfuture/d1-record/commit/9f648b9b5c4fe7e72ca1e99d13c2ba357c6ed33f) Thanks [@christopherstyles](https://github.com/christopherstyles)! - A `d1-record schema` command generates `src/db/schema.ts` from your D1 migrations: each table's columns as `Model({...})` takes them, by Rails-like conventions (declared types, `…_at` timestamps, `TEXT` keys generated in code, literal defaults). `--check` fails CI when it's out of date, and `--watch` regenerates as you edit migrations. It needs Node 22.13 or later.

- [`f895d18`](https://github.com/forestfuture/d1-record/commit/f895d18e4420008dda8cf80dd0b33b4d5e6f3a53) Thanks [@christopherstyles](https://github.com/christopherstyles)! - `d1-record schema` also writes your app's base class when it's missing, `src/models/application-record.ts` (or in `--models <dir>`), as Rails apps have `ApplicationRecord`: `class Product extends ApplicationRecord("products") {}` gets the table's attributes and primary key, typed from the schema. `ApplicationRecord("products", { sku: { default: () => nextSku() }, notes: false })` overrides an attribute's type, nullability or default, or ignores a column (never read or written). `ApplicationRecord({...})` still declares a Model in full. It's built with the library's new `modelFor(tables)`.

- [`6a70ef0`](https://github.com/forestfuture/d1-record/commit/6a70ef026f2123d77d0c3592a2a08facf932f644) Thanks [@christopherstyles](https://github.com/christopherstyles)! - `d1-record schema` recognises migrations written by Drizzle or Prisma and adds notes: those tools can store values differently (numeric timestamps, JSON in plain `TEXT`), so it names each column worth checking against what the generated types say.

- [`553586e`](https://github.com/forestfuture/d1-record/commit/553586eebaab2e35dc55c7a02f5b1dad8ea4ca5b) Thanks [@christopherstyles](https://github.com/christopherstyles)! - Shared behaviour on `ApplicationRecord`, as in Rails: `modelFor(tables, Base)` builds every Model on `Base`, your class extending the new `Model.Base`, so the methods, static methods, callbacks and scopes you write there are inherited by every Model. The generated `application-record.ts` declares an empty `Base` with commented-out examples. `Base` is abstract: `db.model(Base)` throws `InvalidModel`.

- [`beee596`](https://github.com/forestfuture/d1-record/commit/beee5963d6e44029d33ec7378ecf897a1bc07512) Thanks [@christopherstyles](https://github.com/christopherstyles)! - A record built from a Relation starts with what its conditions matched: `where({ label: 7 }).build()`, `create()` and `insert()` now give `label: "7"` instead of throwing `TypeError`. A key copied from another record through an association (a `hasMany` or `hasOne` build, an association's `insert`, `belongsTo` `set()`, or autosave) is cast the same way, so an integer key written into a text foreign key becomes its digits, and an error for one that can't be cast names the association. `includes()` across such keys now finds its records instead of preloading none.
