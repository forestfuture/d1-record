# Active Record for Cloudflare D1

Models, validations, callbacks, associations, and composable queries for Workers, in the spirit of Ruby on Rails, and honest about what D1 can and can’t do.

[Get started](/getting-started) · [Coming from Rails](/coming-from-rails) · [GitHub](https://github.com/forestfuture/d1-record)

<CardGroup cols={2}>
  <Card title="Models, declared once">
    Typed attributes inferred from one declaration, camelCase in your code and snake_case in the
    table, with defaults, timestamps, dates, and JSON converted both ways.
  </Card>
  <Card title="Lazy, composable queries">
    where, comparisons, ordering, pagination, named scopes, and preloading with includes, one query
    per association, never N+1. Hand-written SQL only through a tagged template, so values are
    always bound.
  </Card>
  <Card title="A predictable lifecycle">
    save, create, update, and destroy with validations, Rails’ callback order, abort(), dirty
    tracking, and dependent strategies. Methods that raise end in OrThrow.
  </Card>
  <Card title="Atomic where D1 allows">
    D1 can’t hold a transaction open across awaits, so db.batch writes a prepared set of statements
    and records all at once, or not at all. Keys generated in code let whole graphs save atomically.
  </Card>
</CardGroup>
