# Behavior contract (draft)

The public behavior agreed during design, which the tests must prove. It's written to become the basis of the VitePress documentation site later. Terms follow `GLOSSARY.md`; the reasons for decisions are in `docs/adr/`. Each section names the modules that implement it, and its guide pages where it has them.

## Toolchain

_Code:_ `vite.config.ts`, `package.json`.

- Vite+ `1.0.0`, pinned exactly; upgrade with `vp upgrade`, then `vp migrate`. pnpm 12.6.0 through `devEngines`. Node 24 LTS through `.node-version`.
- Single package `@forestfuture/d1-record` (scoped, published with `access: public`), ESM-only, target ES2022, `.d.ts` emitted, attw `esm-only` profile and publint on every `vp pack`. `"private": true` until we decide to publish. MIT license.
- `src/` is type-checked with `@cloudflare/workers-types` and no Node types. `tests/tsconfig.json` adds Node types.
- Two Vitest projects. `unit` (`tests/unit/**`) is for logic that needs no database. There's no fake executor: tests that involve D1 use the real Miniflare D1 and watch queries through the public `onQuery` hook. `integration` (`tests/integration/**`) gets a fresh in-memory Miniflare D1 per file, with the schema created from `tests/fixtures/schema.sql` (`tests/support/d1.ts`, Miniflare 4). See ADR-0002.
- Pre-commit hooks lint and format staged files. GitHub Actions runs `vp install`, `vp check`, `vp test` and `vp pack` on push to `main`.

## Connecting

_Guide:_ [connecting](../site/guide/connecting.md), [query-databases](../site/guide/query-databases.md), [several-databases](../site/guide/several-databases.md), [read-your-own-writes](../site/guide/read-your-own-writes.md). _Code:_ `src/database.ts`, `src/current-database.ts`, `src/executor.ts`.

A query finds its database one of three ways (#77):

```ts
// 1. The Model's binding, with no setup: static override binding = "DB" (the app's base class names it)
await User.find(id);
await User.where({ isActive: true }).active().toArray();

// 2. The request's database, for a Session, onQuery, or code outside a Worker
await withDatabase(connect(env.DB, { session: bookmark, onQuery }), () => User.find(id));

// 3. An explicit database, always its own
const db = connect(env.DB); // plain binding: every query goes to the primary
const db = connect(env.DB, { session: "first-unconstrained" | "first-primary" | bookmark });
db.bookmark(); // pass to the next request
const users = db.model(User); // a Relation on this database
const models = db.models({ User, Post }); // convenience: models.User has the same type as db.model(User)
```

- A Database with a session sends every query through that one D1 Session: record reads and writes, uniqueness checks, association reads, preloads, statements and batches. So the request reads its own writes even when reads are served by replicas. `session` takes D1's own values: `"first-primary"`, `"first-unconstrained"`, or a bookmark. Apps that want a primary Database and a replica Database call `connect()` twice.
- `db.bookmark()` is the Session's latest bookmark (D1's `getBookmark()`), `null` before its first query. Pass it to the next request's `connect(env.DB, { session: bookmark })` to read at least as new as this request wrote. On a Database opened without a session it throws `NoSession`, since a `null` there would quietly mean "no session" next time.
- **Statics:** every Relation method is a static of every Model (`find`, `findBy`, `where`, `whereNot`, `order`, `first`, `count`, `pluck`, `build`, `create`, `insert`, `insertAll`, `upsert`, `updateAll`, `deleteAll`, the `to…` forms, …), as Rails delegates them to `all`, plus `Model.all()`, the Relation itself, and the Model's scopes (`User.active()`). Each is typed for the class it's called on, so on a subclass it returns that subclass's records. They query the **current database**: the request's, then the Model's binding. Building a Relation never queries, so statics can be called anywhere; running one needs a database.
- **The binding (level 1):** `static binding` names the D1 binding a Model queries when there's no request database, as Rails' `connects_to`; it's inherited, and `d1-record schema` writes it on the app's base class. It's read from `import { env } from "cloudflare:workers"`, loaded only when a query needs it, so the library imports fine in Node. Each binding gets one Database, holding nothing per request (no Session, no listener), shared by every request: safe across concurrent requests in one isolate.
- **The request's database (level 2):** `withDatabase(db | [db, …], fn)` runs `fn` with those databases as the request's own, through Workers' `AsyncLocalStorage`: every query started from a Model inside it, and everything it awaits, uses the one whose D1 binding is that Model's binding, with its Session and `onQuery`. Nested calls add to the outer ones. Outside a Worker (Node, scripts), where there's no binding to match, the request's database serves every Model if there's one, and several are an error. `AsyncLocalStorage` is loaded with `process.getBuiltinModule("node:async_hooks")` when `withDatabase` is first called, so Workers without Node.js compatibility still build; calling it there throws `NoDatabase` naming the setting (a `compatibility_date` of 2026-08-04 or later, or `nodejs_compat`).
- **An explicit database (level 3):** `db.model(X)`, `db.models({...})` and `db.batch([...])` always use `db`, whatever `withDatabase` says.
- **Errors** (`NoDatabase`, saying what to do): a Model with no binding outside `withDatabase`; a binding only available inside a Worker, queried outside one; several request databases outside a Worker; a binding that isn't in the Worker's env (check `d1_databases`). A query at a module's top level fails with Workers' own error: D1 calls happen during a request.
- **One database per query and write (#93).** Whether two handles are one database is decided by the database each resolves to, for every operation: `merge()`, `or()` and a scope's result when the query runs; `batch`, `db.batch`, `save()` and `destroy()` before anything else runs, with no validation, callback or write when they're refused. A save, batch or destroy checks every record it will write: a save's whole autosave graph (the records built through its associations and the new records it points at through `belongsTo`, at every level), and a destroy's dependents. So inside `withDatabase`, a loaded record's association merges with a Model's static Relation, since both resolve to the request's database. Two databases throw `IncompatibleRelation` naming where each came from ("the request's database", "the DB binding's database", "a connect() database"), and `db.batch()` names itself. Every record a save, destroy or batch writes keeps the database it ran on, as the record itself does.
- **`batch([...])`** writes its entries atomically on the database they were built on, as `db.batch` does: the current database for entries from a Model's statics and their records, or one explicit database. Entries from two databases throw `IncompatibleRelation`.
- No request state is ever stored on a Model class (ADR-0012): a request's database lives only in its `AsyncLocalStorage`.
- Every record keeps the Database it was built or loaded through. Records come only from `build()`, `create()` or a query. A record constructed directly with `new User()` throws `NoDatabase` on any operation that needs D1; `User.build(…)` makes one on the current database.

## Declaring a Model

_Guide:_ [models](../site/guide/models.md), [untrusted-input](../site/guide/untrusted-input.md). _Code:_ `src/model.ts`, `src/metadata.ts`, `src/table-names.ts`, `src/verify-model.ts`, `src/permit.ts`.

```ts
class User extends Model({
  id: { type: "string", null: false, generateId: true },
  email: { type: "string", null: false },
  isActive: "boolean", // column: is_active
  htmlUrl: "string", // column: html_url (acronyms are handled)
  legacyId: { type: "integer", column: "person_identifier" },
  createdAt: "datetime",
  updatedAt: "datetime",
}) {
  static primaryKey = "id"; // default

  static active = this.scope((q) => q.where({ isActive: true }));
  static createdAfter = this.scope((q, since: Date) => q.where(sql`created_at > ${since}`));

  static {
    this.validates("email", { presence: true, uniqueness: true });
    this.beforeSave((u) => {
      u.email = u.email.toLowerCase();
    });
  }
}
```

- Attributes are declared once, in the object passed to `Model({...})`, and TypeScript infers the instance properties from it: no `declare`, no second declaration (ADR-0007). An entry is either a type name or `{ type, column?, null?, default?, generateId?, storage? }`. Any other key in an entry is a compile error (#102).
- `tableName` is inferred from the class name by Rails' `tableize`: `underscore`, then pluralized by Active Support's default English inflections (rules, irregulars such as `person` → `people`, uncountables such as `sheep`), ported so tables are named as in Rails: `User` → `users`, `BlogPost` → `blog_posts`, `APIKey` → `api_keys`. An explicit `static tableName` always wins, and is the way to name a table the rules don't (there's no inflection configuration, which would be module-level state, ADR-0012). It's inferred from the class that extends `Model({...})`, so a subclass shares its parent's table, as in Rails. Rails' quirks come with the rules (`Human` → `humen`, `Leaf` → `leafs`), and `static tableName` fixes them. A class with no name to infer from (anonymous, `export default class`, or `Model({...})` itself) throws `InvalidModel` when first used, unless it sets `tableName`. Assigning `tableName` (a static block, or a class field compiled without `useDefineForClassFields`) sets it as declaring it does. Like inferred foreign keys, it needs the class to keep its name when bundled; a Model's own `modelName` for this is #47. When D1 reports "no such table" for an inferred name, the error is an `InvalidModel` saying where the name came from, with D1's error as its `cause`. A declared table that's missing is D1's own error.
- Attributes are camelCase and map automatically to snake_case columns (ADR-0004), using Rails' `underscore` rule, which treats a run of capitals as one word: `createdAt` → `created_at`, `externalAccountId` → `external_account_id`, `htmlURL` → `html_url`, `userID` → `user_id`, `sha256Hash` → `sha256_hash`. `column` overrides the mapping for one attribute.
- Types: `string`, `integer`, `real`, `boolean` (0/1), `datetime` (a `Date`, stored as ISO-8601 TEXT; text with no zone, such as SQLite's `CURRENT_TIMESTAMP` writes, reads as UTC in any time zone; or, with `storage`, as an integer Unix time), `json` (stored as JSON text, in a `TEXT` column as D1 recommends; adding `CHECK (json_valid(column))` makes D1 reject invalid JSON). A column declared `JSON` also works: SQLite stores number-like values in it as numbers, and they still read back as the value written.
- **`storage` (#73).** A `datetime` declared with `storage: "unixSeconds"` or `"unixMilliseconds"` is held in its column as an integer Unix time, as Drizzle's `timestamp` and `timestamp_ms` modes write it. It's still a `Date` in JavaScript, and it's cast like any `datetime` (an ISO string or a `Date`; a number is refused). It's written as an integer (seconds are floored, so a `Date` is kept to the second), read as `new Date(n * 1000)` or `new Date(n)`, and compared as integers by `where`, `gte`, `between` and `order`. `createdAt` and `updatedAt` are set through it. An assignment that stores the same integer isn't a change. `storage` on any other type, or any other value, is a compile error and an `InvalidModel`. Conditions compare the stored integer, so under `unixSeconds` a `Date` with milliseconds compares to the second. A `Date` interpolated into an `sql` fragment has no attribute, so it's written as ISO text and won't compare with the integer; use a number there (`Math.floor(date.getTime() / 1000)`). A typed fragment value is deferred (#142). Reading is strict: an integer-storage column doesn't also read ISO text, since the tools that write epochs don't mix them (checked: Drizzle writes integers by its mode and by `unixepoch()` defaults; Prisma on D1 writes ISO text, so needs no `storage`).
- **Casting (#81).** A value is cast to its attribute's type when it's assigned (`build`, `create`, `assign`, `update`, a property setter, a default) or given to a bulk write (`insert`, `insertAll`, `upsert`, `upsertAll`, `updateAll` and their `to…` forms), so reads, validations and callbacks see the cast value. Only what's unambiguous is accepted; anything else throws `TypeError` (`Sample: "no" isn't a boolean for "enabled"`), and the attribute keeps its value. `null` is always NULL.
  - `boolean`: `true`/`false`, `1`/`0`, `"1"`/`"0"`, and `"true"`/`"false"` or `"on"`/`"off"` in any case.
  - `integer`: a safe integer, or a string that's wholly one (`" 42 "`, `"-7"`, `"+3"`). Not `1.7`, `"12abc"`, `"1e3"`, `""`, `NaN` or past `Number.MAX_SAFE_INTEGER`.
  - `real`: a finite number, or a string that's wholly a decimal number (`"1.5"`, `".5"`, `"-2e3"`).
  - `string`: a string only (not `5`, `true` or a `Date`).
  - `datetime`: a valid `Date`, an ISO-8601 date (`"2026-01-02"`, midnight UTC), or a date and time with `Z` or an `±HH:MM` offset (`T` or a space between them; `T` and `Z` uppercase). Not a time without an offset, a day that doesn't exist (`"2026-02-30"`, with or without a time), other formats or numbers (#73).
  - `json`: any value, unchanged.
  - Unlike Rails, which casts `"12abc"` to `12`, `1.7` to `1`, `5` to `"5"`, any other non-blank string to `true`, and `""` to `nil`: d1-record refuses each, so a value from JSON, a form or a query string is never read as something it isn't.
  - Values inside `sql` fragments aren't cast (they have no attribute), and values read from D1 aren't either.
- Attribute properties are prototype accessors. The first time a Model is used, `db.model(X)` throws `InvalidModel` if it has no table name (an empty `tableName`, or no class name to infer one from), if a class field hides an accessor (e.g. `email!: string` in the class body), or if an attribute is named like a record method (`attributes`, `save`, `constructor`, …). Rename such an attribute and map it with `{ column }`.
- SQL fragments are SQL, so they use column names (``sql`created_at > ${since}` ``), or `column("createdAt")` to look the column up from the attribute (ADR-0006).
- `db.model(X).build(attrs)` makes a new record without querying. Before an attribute is assigned, it reads as `null`. Defaults are evaluated at `build()` (a default returning `undefined` throws `TypeError`, as for any assignment), so app-generated keys (UUID, CUID, ULID) exist before saving.
- **Generated ids (#99).** A `string` attribute declared with `generateId: true` that isn't given gets the Model's `static generateId(attribute)`, wherever a default would run: at `build()`, and in bulk writes (`insert`, `insertAll`, `upsert`, …) for rows that leave it out. `Model.Base.generateId` returns `crypto.randomUUID()`; an app overrides it on its base class (`static override generateId = () => uuidv7()`), or a Model on itself, and it's inherited. It gets the attribute's name, never the record. Its result is cast as an assigned value, so a non-string throws `TypeError`. An attribute with both `generateId` and a `default`, or `generateId` on a type other than `string`, is an `InvalidModel` when the Model is first used, and a compile error. `generateId` is a Model static, so no scope can use the name.
- A record built or created from a Relation starts with that Relation's single equality values: `where({ role: "admin" }).build()` has `role: "admin"`. Arrays, `whereNot`, `or` and `sql` fragments carry nothing over, and explicit attributes win. Those values, and a key copied from another record (a `hasMany` or `hasOne` build, an association's `insert`, `upsert` or `insertAll`, `belongsTo` `set()`, or the key autosave fills in once D1 generates it), are cast as a condition's value is, not as an assigned one (#94): `where({ label: 7 }).build()` has `label: "7"`, and an integer key written into a text foreign key becomes its digits. One that still can't be cast throws `TypeError`, naming the association it came through (`Counted: "abc" isn't an integer for "quantity", the key of code`). Every value the compiler writes is cast as it's bound, so no write depends on a caller casting first. Preloading (`includes`) matches each record's key to its targets the same way, so an integer key finds a text foreign key's digits.
- `record.assign(attrs)` assigns several attributes without saving. `update(attrs)` is `assign` then `save`. An unknown key throws `UnknownAttribute` and an `undefined` value throws `TypeError` (use `null` to store NULL), in `build`, `create`, `assign`, `update`, and when setting a property (`user.email = undefined`).
- **`Model.permit(input, ...names)` (#82)** keeps only the named attributes of untrusted input, as Rails' `params.permit`, so a request can't set any other attribute (mass assignment). `input` is a plain object (its prototype is `Object.prototype` or `null`; only its own keys are read, so `__proto__` never counts), `FormData` or `URLSearchParams` (a repeated key takes its last value, as in Rails); anything else, such as an array, a `Map`, `Headers` or a class instance, throws `TypeError`. A named attribute the input doesn't have is left out; a `null` is kept; every other key is dropped silently. A name that isn't an attribute throws `UnknownAttribute`, and is a compile error. Each value is cast as assigning it would be (#81), so the result, typed `Partial<Pick<attributes, names>>`, is what its type says before it's assigned, and goes straight into `build`, `create` or `update`: a value that can't be cast throws `TypeError`, and so does a file (a `Blob` from a form), which no attribute stores. It's a static, so subclasses and the app's base class have it.
- An insert writes only **assigned** attributes: given to `build`/`create`, set through a property, or filled by a `default`. Anything else is left out, so the column's database default applies. `RETURNING *` then loads what D1 actually stored, including generated keys and defaults.
- An update writes only the attributes that changed. A save with nothing changed sends no statement. Changing the primary key is allowed, and the UPDATE finds the row by the key as last loaded or saved.
- If the row is already gone (e.g. another request deleted it), `save` and `destroy` still succeed. `reload()` throws `RecordNotFound`, since there's nothing to load, and so does reloading a record that was never saved.
- Timestamps are on when `createdAt`/`updatedAt` are declared as `datetime` attributes. They're set in JavaScript (`new Date()`) just before the write is compiled: both on insert, and `updatedAt` on an update that changes something. A clean save leaves `updatedAt` alone. A timestamp assigned explicitly is kept.
- Keys that aren't declared attributes throw `UnknownAttribute` in `build`, `create`, `update` and `where`, and are compile errors where the types can see them.

## The generated schema

_Guide:_ [schema](../site/guide/schema.md), [adopt-a-database](../site/guide/adopt-a-database.md), [command-line](../site/guide/command-line.md). _Code:_ `cli/schema/`, `src/schema-model.ts`.

`npx d1-record schema` (Node 22.13+) writes `src/db/schema.ts` from the project's D1 migrations, found through its Wrangler config (`migrations_dir`, `migrations_pattern`, `migrations_table`; one file per binding when there are several). It applies them to an in-memory SQLite database and converts each table's columns to attributes by convention: the declared type first (`INTEGER`, `TEXT`, `REAL`, `BOOLEAN`, `DATETIME`/`TIMESTAMP`/`DATE`, `JSON`, a `TEXT` with `CHECK (json_valid(…))` as `json`), then, only for a column declared exactly `TEXT` or `INTEGER`, its name (`…_at` `TEXT` → `datetime`, `is_…`/`has_…` `INTEGER` → `boolean`, printed as a note). `NOT NULL` → `null: false`; literal defaults are copied, and a `TEXT` primary key without a literal default gets `generateId: true`. `NUMERIC`/`DECIMAL`, `BLOB`, composite or missing primary keys, and names that would collide are errors that say what to do; a broken migration is reported by file name and the last good file is kept. A `DATETIME` or `TIMESTAMP` column whose default is a number or an epoch function (`DEFAULT 0`, `unixepoch()`, `strftime('%s', …)`) gets a note naming the `storage` override, whatever tool wrote the migration. Migrations written by Drizzle or Prisma (recognized by `drizzle.config.*`, `schema.prisma`, `prisma/schema.prisma` or `prisma.config.ts` in the project or a folder above it up to the repository's root, or by the `--> statement-breakpoint` and `-- CreateTable` lines they write) add more notes, since those tools can store values differently. The first names the tool and links #73. Then each column worth checking gets one, whether it's named in snake_case or camelCase. An `INTEGER` named `…_at`/`…At` may hold a Unix timestamp, and its note shows the `storage` override that reads it as a `Date`, naming Drizzle's `timestamp` and `timestamp_ms` modes for Drizzle. A `TEXT` without a `json_valid` check named `…_json`/`…Json`, `metadata`, `settings`, `payload` or `properties` may hold JSON. A Prisma `datetime` gets no note, since Prisma writes ISO text to D1. These per-column notes come only with a recognized tool's migrations: they're hints, where the `is_…` note reports a guess the generator made for you. Notes come with a file that's written, so they don't repeat when it's up to date, while watching, or with `--check`. Migrations in folders (`migrations/0000_init/migration.sql`, as Drizzle writes them) with no `migrations_pattern` to find them get Wrangler's hint to set one, every time. It never replaces a file it didn't write (one without its "Generated by" header, such as a Drizzle schema), and never writes a file next to a folder of the same name (`src/db/schema.ts` beside a Drizzle `src/db/schema/`), whose imports it would take over; either is an error suggesting `--out`, and the generators check it before writing anything. `--check` fails when the file is stale (it compares a fingerprint of the schema, so formatting doesn't matter), and `--watch` regenerates as migrations change.

```ts
// src/models/application-record.ts (written once by `d1-record schema`, then the app's)
import { modelFor } from "@forestfuture/d1-record";
import { tables } from "../db/schema"; // generated

export const ApplicationRecord = modelFor(tables);
```

```ts
// src/models/product.ts
import { belongsTo } from "@forestfuture/d1-record";
import { ApplicationRecord } from "./application-record";

class Product extends ApplicationRecord("products") {
  user = belongsTo(User);
}

class Listing extends ApplicationRecord("products", {
  available: "integer", // a type alone
  tagline: { null: false, default: () => "New!" }, // type, null and default
  notes: false, // ignored
}) {}

class Visit extends ApplicationRecord({ id: "integer", path: "string" }) {} // the library's Model({...}), unchanged
```

- The generated `schema.ts` is a document, like Rails' `schema.rb`: each table's attributes and `tables`, importing nothing. When it's missing, `d1-record schema` also writes the app's base class, `src/models/application-record.ts` (`ApplicationRecord = modelFor(tables)`), as Rails apps have `ApplicationRecord`; it never writes over it, so it's the app's to edit (`--check` writes nothing). With several databases, each binding gets its own, named as Rails names them (`LOGS` → `LogsRecord` in `src/models/logs-record.ts`, `MY_DB` → `MyDbRecord`); two bindings whose names would give the same base class (`DB` and `db`) are an error. `--models <dir>` puts it in another folder (`src/app/models`); the generators take the same flag, so Models and their base class stay together. `modelFor(tables)` is the library's.
- `ApplicationRecord("products")` is a base class bound to that table: its attributes and `primaryKey` come from the schema, and `tableName` is the argument, never inferred, so it doesn't depend on the class name. Subclasses share it. Setting `tableName` to another table on such a Model throws `InvalidModel` when it's first used, since its attributes are that table's; `primaryKey` can still be set, and must name an attribute.
- The table is typed from the schema: a name that isn't one is a compile error (and an `InvalidModel` if the types are bypassed).
- Overrides are keyed by the generated attribute names, and typed from them: an unknown key is a compile error and an `InvalidModel`. An override is a type name (`"integer"`), or `{ type?, null?, default?, generateId?, storage? }` merged into the generated spec; a key left `undefined` changes nothing, the column can't change, and an attribute can't be added. Anything else is an `InvalidModel` naming the attribute, checked when `ApplicationRecord("…")` is called, so plain JavaScript and casts get the same rules. The record's TypeScript types follow the merged spec; like `Model({...})`'s, a `default` isn't type-checked against the attribute's type yet (#74). An override that changes the `type` without giving a `default` drops the generated one, which was for the old type: the column's own default applies on insert (#81). A `default` that returns a value the type can't cast throws `TypeError` when a record is built. A `default` replaces a generated `generateId`, and `generateId` a generated `default`; changing the `type` drops `generateId` too; `generateId: false` turns it off, and `generateId: true` turns it on for a `string` attribute. An override that leaves `generateId` with a `default`, or on another type, is an `InvalidModel` when `ApplicationRecord("…")` is called (#99).
- `false` ignores a column, as Rails' `ignored_columns`: it isn't an attribute, so it's never typed, assigned or written, and the Model's queries name its columns instead of `*` (`SELECT` and `RETURNING`), so it's never read. The primary key can't be ignored. Inserts leave an ignored column to its database default, so a `NOT NULL` column without one makes them fail.
- `ApplicationRecord({...})` is the library's `Model({...})` built on the same base, for views and tables outside the migrations. A Model can also extend the library's `Model({...})` directly.
- **Shared behavior**, as on Rails' `ApplicationRecord`: `modelFor(tables, Base)` builds every Model on `Base`, a class the app writes extending `Model.Base` (the library's base class; `modelFor(tables)` uses it directly). The generated `application-record.ts` declares an empty `Base`, with commented-out examples of a shared method, scope, and callback, and of `onQuery`, `filterAttributes`, and `generateId`. Instance methods and getters, static methods, callbacks declared in its `static {}` (they run for every Model, before the Model's own, in declaration order), and scopes (`static newest = this.scope(…)`) are inherited, by Models declared either way. A Model's own scopes add to the base's, as scopes inherit down any chain of classes. Once a Model is used, the classes it inherits declarations from (the base class too) are sealed as it is. Inside `Base`, `this` is typed as `Base`: it has every record method, but no attributes, since those differ by table (read them with `this.attributes()`), so shared scopes use `sql` fragments and `this.validates(…)`, which names an attribute, isn't available there; shared validation logic goes in a callback. `Base` is abstract, as Rails' `abstract_class`: it has no table, so `db.model(Base)` throws `InvalidModel`.

### Generators

_Guide:_ [generators](../site/guide/generators.md), [change-a-table](../site/guide/change-a-table.md), [command-line](../site/guide/command-line.md). _Code:_ `cli/generate/`.

`npx d1-record g model <Name> [columns]` writes a `CREATE TABLE` migration and a Model; `npx d1-record g migration <Name> [columns]` writes a migration whose name says what it does. Both then regenerate the schema and print the next step (`npx wrangler d1 migrations apply <database_name> --local`); neither applies migrations.

- **Columns** are `name:type`: `string` (the default, so `title` and `slug:index` are strings), `integer`, `real`, `boolean`, `datetime`, `json` or `references`; then `!` for `NOT NULL`, `=value` for a literal default (`string`, `integer`, `real` and `boolean` only, and it may hold a `:`; Rails' generators have no such syntax), and `:unique` or `:index` for an index named as Rails names it (`index_products_on_sku`). Names are written in snake_case whichever way they're given. Types write `TEXT`, `INTEGER`, `REAL`, `BOOLEAN`, `DATETIME` and `TEXT CHECK (json_valid(…))`. `user:references` writes `user_id`, typed like the `users` key (`TEXT` if `users` isn't in the migrations yet, with a note), `NOT NULL` with `REFERENCES users (id)`, and an index. Names SQLite reserves are quoted.
- **Names** are letters, digits and `_`, starting with a letter; anything else is refused, so a file can only land in the migrations or Models folder. A Model's name is made singular, as Rails makes it (`g model line_items` writes `LineItem`, with a note), and a migration's table plural (`CreateWidget` creates `widgets`).
- **`g model LineItem`** creates `line_items` with `id TEXT PRIMARY KEY NOT NULL` (a key generated in code; `--id integer` for `INTEGER PRIMARY KEY`, generated by D1), the columns, and `created_at`/`updated_at DATETIME NOT NULL` (`--no-timestamps` leaves them out). It writes `src/models/line-item.ts` with `export class LineItem extends ApplicationRecord("line_items") {}` (the database's base class), a `belongsTo` field for each reference, and extensionless imports of the base class and of each target's file. `--models <dir>` writes it (and expects the base class) in another folder, as `d1-record schema --models` does; `--out` names the schema file to regenerate, as for `d1-record schema`. `--models src/models.ts` appends the class to one file instead, with the base class beside that file, adding the `belongsTo` and base-class imports if they're missing; a file that imports a base class of that name from somewhere else is refused.
- **`g migration`** reads its name as Rails does (`AddSkuToProducts` or `add_sku_to_products`): `Create<Table>` creates the table as `g model` does, `Add…To<Table>` adds the columns (a reference added this way can be `NULL`, as Rails' `add_reference`), `Remove…From<Table>` drops them, after `DROP INDEX IF EXISTS` for the index a generator would have named, and any other name is an empty migration. Adding a `NOT NULL` column without a default is refused, since SQLite can't.
- **Files** are numbered as Wrangler numbers them: the highest leading number in the migrations folder, plus one, in four digits (`0008_add_sku_to_products.sql`). A file the config's `migrations_pattern` wouldn't match is refused, as `wrangler d1 migrations create` refuses it.
- **Nothing is written** unless the new migration applies after the existing ones (in memory, as `d1-record schema` applies them) and the Model file is new (or, for `--models` with one file, doesn't have the class yet). Otherwise the command prints why, then "Wrote nothing". With several D1 databases, `--database <binding>` chooses one, and the Model imports that database's schema file.

## Console

_Guide:_ [console](../site/guide/console.md), [command-line](../site/guide/command-line.md). _Code:_ `cli/console/`. See ADR-0014.

- `d1-record console` (also `c`; options `--database`, `--models`, `--config`, `--no-history`, `--history`, `--verbose`, `--remote`, `--yes`, `-e`/`--eval`) opens the project's D1 database in a REPL (#104). **Local unless `--remote`**: `getPlatformProxy` is called with `remoteBindings: false`, so a binding marked `remote: true` still opens locally.
- **The database** is the only `d1_databases` binding in the Wrangler config, or the one `--database` names; with several and no `--database`, or a name the config doesn't bind, it prints why and exits 1, as `g` does. Only that binding is started: `getPlatformProxy` is given a temporary Wrangler config holding the chosen `d1_databases` entry as the project's config has it (removed when the console ends), because it starts every binding a config declares (Durable Objects, services, secrets from `.dev.vars`), with their warnings and failures. State is read and written in `<config dir>/.wrangler/state/v3`, where `wrangler dev` keeps it (not relative to the working directory, as `getPlatformProxy`'s own default is).
- **The project's own code.** `wrangler` and `@forestfuture/d1-record` are resolved from the project, never from the CLI's copy, so the Models and the console share one library instance (ADR-0014). One `jiti`, based in the project, loads the Models (TypeScript, extensionless imports, `tsconfig.json` `paths`, and the library itself). Without either package installed, the console says so.
- **The Models** are the exported classes (extending `Model.Base`) of every `.ts` file in `--models` (`src/models`), or of the one file `--models` names. Each is in scope by its class name, with `db` (the connected `Database`). No Models, a file that throws on load (named in the message), or no folder: it prints why and exits 1.
- **Each line** is evaluated inside `withDatabase(db, …)`, so Models' statics and records need no database argument. Top-level `await` works; `const` and `let` last for the session. A result prints as `#=> ` and its `util.inspect` (colored on a terminal, so a record prints as under Printing); an uncaught error prints as Node prints it, without `#=>`, and the session carries on.
- **Lines pasted or piped** run in order, each after the one before, and the session finishes them before it ends. The REPL closes as soon as its input ends, so piped input is held back until they are done.
- **History** is kept on a terminal only, in `<config dir>/.wrangler/d1-record-history`; `--no-history` keeps nothing (a line can hold a token or an email). A remote session keeps none unless `--history` is given, and then in `<config dir>/.wrangler/d1-record-history-remote`, so an up arrow never offers a line typed against the real database to a local session; `--history` with `--no-history` is a usage error.
- **The prompt** is `local> ` or `remote> `, the latter red on a terminal.
- **`--remote`** opens the chosen binding on the project's real D1 through Wrangler's remote proxy: the temporary config's entry is marked `remote: true` whatever the project's config says, `remoteBindings` is `true`, and nothing is persisted locally. The temporary config carries the project's `account_id`. The database is the one Wrangler uses, `preview_database_id` before `database_id`; the session says "Remote preview database" when it is the preview one. Before Wrangler is started (so before any sign-in; the project's own Models have been loaded, which needs no database) it names the database and its id and asks for its `database_name` (the binding's name when there is none) to be typed: anything else, a blank line, or the end of the input cancels (`Not opened.`, exit 1; a database with an empty `database_name` is named by its binding, so an empty answer is never the name). The one line is read and everything typed or pasted behind it is dropped, from the answer until the database is open (a terminal delivers a paste a line at a time, so those lines would otherwise reach the session and run on the real database). `--yes` skips the question (and is the only way to open it off a terminal, which otherwise exits 1 saying so; a terminal is stdin and stdout both being one, so a pipe on either end can't answer); `--yes` without `--remote` is a usage error. A binding with no `database_id` exits 1 before asking. When Cloudflare refuses, Wrangler's message is printed with how to sign in (`wrangler login`, or `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`). It starts by printing `Remote database DB (name, id …)`.
- **Console commands** are `.name` REPL commands (listed by `.help`), run in line order like any line, that print one message and show the next prompt. Two exist (#104):
  - **`.reload`**, and the bare line `reload!`, read the project's Models again: its own modules (everything the loader read under the project's folder, not `node_modules`) are forgotten and the Model files read afresh, so edits, added and removed files show. The library and `db` are not reloaded, so the Models stay Models of the same library. The session's names are updated (Models removed from the folder are no longer named; other variables are untouched) and it prints `Reloaded: A, B`. A file that fails prints `Couldn't load <file>: <message>`, or no Models says why, and the loaded Models stay as they were. Records and values already held keep their old class.
  - **`.verbose`** (and the bare line `verbose!`) toggles, `.verbose on` and `.verbose off` set: each statement prints before the line's result as `  Model  1.2ms  SQL  [ params ]` (or `failed` and the message), dim on a terminal, to the console's output stream. `--verbose` starts it on. It is the database's own `onQuery` (so params are the ones listeners get, filtered ones `[FILTERED]`), and the app's base-class `onQuery` still fires after it. Replies `SQL logging on` or `SQL logging off`.
- **`-e <code>`** (`--eval`) runs the code once instead of opening a session, and exits (#105). It is evaluated as a line is, so top-level `await`, `const`, the Models and `db` work, and each statement runs inside `withDatabase`. **stdout holds the code's `console.log` output, then the result**: a string as it is, anything else as `util.inspect` shows it (colored only when stdout is a terminal), no `#=> `, nothing for `undefined`; with several statements, the last value. The code's `console` is its own: `console.log` and `console.info` go to stdout, `console.error` and `console.warn` to stderr. **stderr holds everything else**: the database and Models banner, `--verbose` statement lines, refusals to start, and a failure's stack (`util.inspect` of what was thrown or rejected). The remote confirmation's question is asked on stdout, which is a terminal whenever it is asked. Success exits 0. A throw, a rejected `await`, an unfinished statement, a refusal, or a database that won't close exits 1, prints no result, and no later statement runs; the output is written after the database is closed, so a result is never printed for a run that fails to close. A console command line (`reload!`, `verbose!`) or REPL command (`.help`) runs and prints nothing. A promise the code doesn't await may not finish before the console exits, and a rejection that arrives after the code has finished is not reported; there is no time limit. It keeps no history and ignores what is piped to it. `-e` given twice, or with only whitespace, is a usage error. With `--remote` the same consent applies (a terminal to answer on, else `--yes`): `$(…)` makes stdout a pipe, so it needs `--yes`. Piped lines without `-e` are unchanged: the banner, prompts and results on stdout, and exit 0 even when a line fails. Code: `cli/console/script.ts`.
- **Leaving:** a line that is just `quit` or `exit` (also `.exit`, and Ctrl-D on a terminal) closes the session without evaluating anything, so nothing prints, and lines queued after it are not run. They are matched as whole lines, so `quit()` or `await quit` are not.
- **Ctrl-C** on a terminal stops a line that is still running (`breakEvalOnSigint`), such as an `await` that never ends; the session carries on.
- **When it can't start** it prints why and exits 1: a binding Wrangler can't open (with Wrangler's reason), or `wrangler` or the library that is found but throws on load (named as that, not as "not installed").
- **Needs** Node 22.13 or later (as every command). It starts by printing the database (`Local database DB (.wrangler/state)`) and the Models (`Models: Post, User`).
- Not yet: `--sandbox` (#107, which records why it is a discardable copy and not a transaction).

## Scopes

_Guide:_ [querying](../site/guide/querying.md), [models](../site/guide/models.md). _Code:_ `src/scoped-relation.ts`.

- Declared one static each, as Rails' `scope :active, -> { … }`: `static active = this.scope((q, ...args) => q…)`. A scope receives the current Relation and its arguments and returns a changed Relation of the **same Model**; anything else throws `TypeError` naming the scope. The Relation it returns may start again from the Model's statics: it must be on the same database when the query runs, or it throws `IncompatibleRelation` naming the scope (#93), so a query never silently moves to another database.
- Callable as a static (`User.active()`, on the current database, #77), on `db.model(X)`, and on any Relation of that Model, and chainable with everything: `User.where(…).active().createdAfter(d).order(…)`. Scope calls are typed, including what a static scope returns when called on a subclass (`Admin.active()` is a Relation of `Admin`): a wrong argument type or an unknown scope name is a compile error.
- Calling a scope never queries. A scope's arguments, and anything it computes such as `new Date()`, are evaluated when it's called, not when the class is defined.
- Inside a scope body, `q` has every Relation method but not the Model's other scopes (their types would refer to themselves). To reuse logic, share a plain function between scopes.
- Scopes are statics, so they inherit as statics do, down any chain of classes, in types and at runtime: a subclass has its parent's scopes plus its own, and a same-named one (`static override admins = this.scope(…)`) replaces the parent's. The parent never gains the subclass's. Scopes on the app's base class (`ApplicationRecord`'s `Base`) are every Model's.
- A scope whose body names its own class needs its type written out, as any self-reference does: `static elsewhere: ScopeStatic<[]> = this.scope(…)` (`ScopeStatic<[...arguments]>`).
- A scope can't use any name a Relation already has: its methods (`where`, `count`, …), the standard object ones (`constructor`, `toString`, …), or `then`, which would make Relations awaitable; nor a Model static's (`validates`, `beforeSave`, `scope`, `all`, …). `db.model(X)` throws `InvalidModel` for such a name.
- Scopes are fixed once a Model is used: replacing one afterwards (`User.active = User.scope(…)`) makes `db.model(X)` throw `InvalidModel`.
- Default scopes and `unscoped` are deferred (#25).

## Inheritance, shared behavior and serialization

_Guide:_ [shared-behavior](../site/guide/shared-behavior.md), [models](../site/guide/models.md). _Code:_ `src/ancestors.ts`, `src/declarations.ts`, `src/model.ts`, `src/verify-model.ts`.

- A subclass (`class Admin extends User`) inherits a copy of its parent's attributes, validations, callbacks, scopes and associations. Declaring more on the child never changes the parent. Single-table inheritance is out of scope.
- Share behavior between all Models on the app's base class, `ApplicationRecord`'s `Base` (see "Shared behavior" under The generated schema), as Rails does. Behavior only some Models share can be a plain function called from their `static {}` (e.g. `audited(this)`). A `.with({...})` helper for adding attributes to a subclass of a shared base is deferred (#14).
- `attributes()` returns a plain object of loaded camelCase attributes with JavaScript values. `toJSON()` returns the same object, but with a `Date` as an ISO string, so `Response.json(user)` works. It leaves out the Model's **hidden attributes** (#101): `static hiddenAttributes: readonly string[]`, exact camelCase names, empty on `Model.Base`, inherited, and replaced (not merged) by a Model's or the app's base class's own list (`[...Base.hiddenAttributes, "apiKey"]`). It's read when `toJSON()` runs, and doesn't touch `attributes()`, which stays whole. A name in a Model's own list that the Model has no attribute for is an `InvalidModel` when the Model is first used; names listed by a class without attributes (the app's base class, `Model.Base`) are ignored where a Model lacks them, even when spread into the Model's own list. A name a partial record didn't load is harmless. The generated `application-record.ts` shows a commented-out example. Associations are never included automatically.
- **Printing (#104):** a record and a Relation print readably under `Symbol.for("nodejs.util.inspect.custom")`, so Node's `util.inspect`, `console.log`, the REPL and workerd's `node:util` use it, with the `depth`, `colors` and `stylize` they pass. A record prints `Name { attribute: value, … }` with its loaded attributes (a new record's unassigned ones as `null`; a partial record's only the columns it loaded), and its values printed by the runtime's own `inspect`. A filtered attribute's non-null value prints as `[FILTERED]`, unquoted and in the special color; `null` prints as `null`. On a persisted record, an attribute that differs from its Snapshot prints `after (was before)`, a filtered one prints `[FILTERED] (changed)` (also when it became `null`, so the old value never shows), and an attribute a partial record never loaded prints `after (changed)`, since its value before is unknown; a new record flags nothing. `hiddenAttributes` don't affect it, and associations aren't printed. Nested deeper than `depth` allows, a record prints as `[Name]`. A Relation prints `Relation<Name> { sql, params }`: the SELECT `toSql()` shows, never sent (printing is synchronous, so it can't load records), with a filtered attribute's param as `[FILTERED]`; past `depth`, `[Relation]`. A record's `errors` print `Errors [ { attribute, type, message }, … ]` (`Errors []` when there are none; `[Errors]` past `depth`). Code: `src/record-inspect.ts`, `src/relation-inspect.ts`, `src/errors-collection.ts`.

## Change tracking

_Guide:_ [models](../site/guide/models.md). _Code:_ `src/record-state.ts`.

- Change detection compares each attribute's current serialized value with the value last loaded or saved, so in-place changes to `json` values and `Date`s are detected.
- `isChanged()`, `changed()` → `["email"]`, `changedAttributes()` → `{ email: old }`, `changes()` → `{ email: [old, new] }`.
- `savedChanges()` holds the changes from the last **successful** save (`{}` after a clean save). After `create`, that's everything the new row holds, including what D1 filled in (the generated key, column defaults), each changed from `null`. A failed save doesn't change it. `changes()` and `savedChanges()` return copies, so editing the record afterwards never alters them. Use it in `after*` callbacks, where the record is already clean.
- A new record's changes are its assigned attributes, each changed from `null`.
- Per attribute, as Rails' generated helpers (with the attribute's name, typed from the Model): `attributeWas("email")` is the value before the unsaved change (a new record's is its declared default, or `null`, as in Rails, so it agrees with `restoreAttributes`; `changes()` still reports a new record's changes from `null`, #41); `isAttributeChanged("email", { from?, to? })` and `willSaveChangeTo("email", { from?, to? })` check an unsaved change, for before-callbacks; `savedChangeTo("email")` (`[before, after]` or `undefined`), `hasSavedChangeTo("email", { from?, to? })` and `attributeBeforeLastSave("email")` read the last save, for after-callbacks. `from`/`to` compare as stored, so dates by time and `json` by content. Every one of them throws `MissingAttribute` for an attribute that wasn't loaded, as reading it does.
- `restoreAttributes(names?)` undoes unsaved changes, to the named attributes or all: a persisted record's go back to their stored values, and a new record's to their declared defaults or generated ids (or `null`), as in Rails.

## Associations

_Guide:_ [associations](../site/guide/associations.md). _Code:_ `src/association-fields.ts`, `src/associations.ts`, `src/association-writers.ts`, `src/foreign-keys.ts`, `src/resolved-association.ts`, `src/owned-collection.ts`, `src/autosave.ts`, `src/dependents.ts`, `src/preload.ts`.

```ts
class User extends Model({ id: { type: "integer", null: false } }) {
  posts = hasMany(Post); // foreign key inferred: userId
  profile = hasOne(Profile);
}

class Post extends Model({ id: "integer", userId: "integer" }) {
  author = belongsTo(User, { foreignKey: "userId" }); // "author" would infer authorId
}
```

- `belongsTo`, `hasMany` and `hasOne` are declared as record fields (ADR-0008): `posts = hasMany(Post, {...})`, imported from the package. The field's name is the association's name, and TypeScript infers the accessor's type from it: no `declare` line. The target class is passed directly, in any declaration order, since a field's initializer only runs when a record is made.
- The library reads a Model's associations once, from a probe record made on first use, and removes the fields from the records it builds, so the accessors on the prototype answer. On a record constructed directly (`new User()`), calling an association, or its `set`/`build`/`create`/`createOrThrow`, throws `NoDatabase`. Plain (non-association) class fields stay on records as declared. Fields compiled as assignments (without `useDefineForClassFields`) work the same.
- `foreignKey` names an attribute, not a column, like everything outside `sql` fragments (so `foreignKey: "userId"` where Rails writes `foreign_key: :user_id`): the owner's for `belongsTo`, the target's for `hasMany`/`hasOne`. Left out, it's inferred by Rails' convention: a `belongsTo`'s name + `Id` (`author` → `authorId`), or for a `hasMany`/`hasOne` the owner's class name + `Id`, through the same `underscore` rule as columns (`User` → `userId`, `APIKey` → `apiKeyId`, `BlogPost` → `blogPostId`). An explicit `foreignKey` always wins. A `hasMany`/`hasOne`'s inferred key comes from the class that extends `Model({...})`, the same class the table name comes from, so a subclass's association infers its parent's key (Rails uses the declaring class).
- Inferring from the class name needs the class to keep its name when bundled. Wrangler keeps names by default, even with `--minify` (its `keep_names` setting); a bundler that renames classes turns `User` into something like `e`, and the inferred `eId` fails loudly at first use. The `InvalidModel` message names the attribute it looked for and where it came from ("inferred from the class name User") and suggests `foreignKey`. A Model's own `modelName` for this is #47.
- `primaryKey` is the attribute the foreign key points at. It defaults to the target's primary key for `belongsTo`, and the owner's for `hasMany`/`hasOne`. Keys aren't type-checked. They're checked when the Model is first used, as are an association named like an attribute or a record method/property, and a target that isn't a Model: all `InvalidModel`.
- `await post.author()` and `await user.profile()` resolve to a record or `null`. `user.posts()` returns a lazy Relation of the target, with its scopes and every Relation method. All three query through the owner's Database. Without a query: `belongsTo` resolves to `null` when its foreign key is `null`, and `hasOne`/`hasMany` resolve to `null`/an empty Relation when the owner has no key (it's unsaved, or its key attribute is `null`). A `belongsTo` on an unsaved record whose foreign key is set loads the target, as in Rails.
- Writing through a `belongsTo` or `hasOne`, as Rails' `post.author = user`, `build_author` and `build_profile` do: the accessor also has methods, so `await post.author()` is unchanged.
  - `post.author.set(user)` sets the post's foreign key to the user's key and makes the user the loaded `author` (no query to read it). `set(null)` clears both. A record of another Model throws `TypeError`. It's written when the post is saved.
  - `post.author.build(attrs)` makes a new author the post points at. `post.author.create(attrs)`/`createOrThrow` save the author at once, then point the post at it (the post itself isn't saved).
  - `user.profile.build(attrs)` makes a new profile pointing at the user, loaded as its `profile` and autosaved with it. An unsaved owner's built profile stays its loaded `profile` after the owner saves it. `create`/`createOrThrow` save it at once, and throw `RecordNotSaved` on an unsaved owner, as in Rails; a created profile that doesn't save is kept, so saving the owner tries it again. An existing profile is left as it is (Rails' replacement rules are #40), so a unique foreign key fails loudly rather than losing anything.
  - A new record set or built through a `belongsTo` is validated with its owner ("Author is invalid") and saved **before** it, then the owner's foreign key is filled in, as Rails' belongs_to autosave does. It's filled in even if the record was saved on its own in between. When its key is generated in code, the owner's foreign key holds it from `set`/`build` on, so the owner's `beforeSave` sees it. When D1 generates it, the owner's before-callbacks run before it exists (they see `null`): a save prepares everything, callbacks included, before writing anything. When its key is known in advance (generated in code), both writes are one atomic batch; when D1 generates it, the new record is written first, then the owner. In `db.batch`, that's only allowed when the key is known (`RecordNotSaved` otherwise).
- A loaded association is cached on the record, as in Rails: `await post.author()` and `await user.profile()` query once (a `null` result included), and `await user.posts().toArray()` loads the collection once, in target primary-key order. Preloading with `includes` fills the same cache. Each cached value remembers the key it was loaded for, so changing a foreign key (`post.userId = 2`) makes the next read query again, preloaded or not. `reload()` clears the cache and discards records built through the associations, as Rails' reload does; `save()` keeps the cache. `await record.reloadAssociation("author")` queries again, replaces what's cached (discarding that association's built records) and returns it (Rails' `reload_author`, and `user.posts.reload`).
- Records built or created through `user.posts()` get the owner's key. On an unsaved owner, `create`/`createOrThrow` throw `RecordNotSaved`, as in Rails, and `build` gives a record whose key is filled in when the owner is saved (autosave, below).
- **Autosave**, as Rails' `has_many` does by default: a record built through a `hasMany` joins the association at once, and saving the owner saves the ones still new, with its key. An unsaved owner's `user.posts().toArray()` returns its built records without a query; a saved owner's loaded collection is its stored records followed by the built ones, however and whenever it's loaded. (As in Rails, `pluck` and `count` on a collection that isn't loaded query the database, so they leave built records out.)
  - They're validated with the owner: an invalid one makes the owner invalid, with "Posts is invalid" on the owner and its own errors on the record.
  - The order is the owner's validation (the records included), the owner's before-callbacks, the records' before-callbacks, the writes, then the owner's after-callbacks and the records'. An owner with no changes of its own still saves its built records.
  - Autosave reaches every level: a built record's own built records are saved too, validated one after another in the order they were built, as Rails does.
  - When the owner's key is known before its INSERT (a key generated in code, or an owner that's already saved), the owner and its records are written in one atomic batch. When D1 generates the key, the owner is written first and its records follow in the next batch (and theirs in the one after, a level at a time): that isn't atomic between the batches, so a record that then fails (only a constraint error can, after validation) throws with the owner saved and the record still new. The after-callbacks of everything already written still run first. Generate keys in code where the whole graph must be atomic.
  - In `db.batch`, `owner.toSave()` autosaves only when the owner's key is known; otherwise it throws `RecordNotSaved`, since the batch couldn't be atomic.
  - Records created with `create` aren't autosaved (they're saved at once), and a built record saved on its own isn't saved again. In `db.batch`, each record is written once: listing a record twice, or listing a record its owner's autosave already saves, doesn't write it again. List the owner rather than its built records: a built record listed before its owner is saved on its own, without the owner's key. `autosave: true` (changed records, marking for destruction) is #37, and `validate: false` is #39.
- `includes("posts", "profile")` and nested `includes({ posts: "comments" })` or `includes({ posts: ["comments", "tags"] })` preload associations for every record loaded, by `toArray`, `first`, `last`, `take`, `find` and `findBy`. Names are typed from the association fields, and an unknown one throws `UnknownAssociation`. Each association is loaded with one `WHERE key IN (…)` query, whatever the number of parents (the keys are one bound value), never one query per record, as in Rails. Keys preloading needs are loaded even if `select` leaves them out; since adding them would undo a `distinct`, `includes` with `select(...).distinct()` throws `IncompatibleRelation`. `includes` on `none()` sends nothing. Models reached only through `includes` are checked and prepared like any other.
- On a loaded `hasMany`, `toArray`, `first`, `last`, `take` and `pluck` answer from the loaded records without a query. `count` always queries, like Rails' `count`; `size()` uses the loaded records. Chaining further (`user.posts().published()`, …) queries as normal and doesn't change the cache. `create` through a loaded `hasMany`, narrowed or not (`user.posts().where(…).create(…)`), appends the new record when it saves, as Rails' association and association relation do. `insert`, `updateAll` and `deleteAll` built through it clear the cache. `build` appends the new, unsaved record (see autosave). A record destroyed some other way stays in an owner's cached collection until it's reloaded, as in Rails. A loaded `hasMany`'s records are in its scope's order, then target primary-key order, and a `hasOne` (lazy, preloaded or as a dependent) picks the first record in that same order, so ties resolve alike everywhere. A `belongsTo` with a `null` key, or a `hasOne` whose owner has no key, reads as `null` without a query, and that `null` counts as loaded.
- `record.loaded("posts")` returns a loaded association synchronously (records for a `hasMany`, a record or `null` otherwise), typed from its field. A list is returned as a copy. It throws `AssociationNotLoaded` unless the association was preloaded or already read, for the key the record holds now. `record.isLoaded("posts")` is the predicate (Rails' `association(:posts).loaded?`).
- `or()` needs the same `includes`, and `merge()` combines both sides' includes.
- A subclass has its parent's associations, inherited as fields, plus its own. Redeclaring a field replaces the parent's association; removing one isn't possible, as in Rails.
- `user.posts().insert(attrs)`, `updateAll(...)` and `deleteAll()` write through the association, and their `to…` forms build statements (see _Batches_). As in Rails' `has_many`, `deleteAll()` on the association itself deletes the records when its `dependent:` is `"destroy"` or `"deleteAll"`, and otherwise sets their foreign key to `NULL` (a NOT NULL foreign key raises `NotNullViolation`). Once narrowed (`user.posts().where(...)`, `.limit(…)`, a scope), `deleteAll()` deletes, as a Rails association relation does. For an owner without a key, `insert` rejects with `RecordNotSaved` (`toInsert` throws it), and `updateAll`/`deleteAll` match nothing.
- An association can declare a scope, as Rails' `has_many :posts, -> { order(created_at: :desc) }`: `hasMany(Post, { scope: (q) => q.order({ createdAt: "desc" }) })`, on `hasMany`, `hasOne` and `belongsTo`. `q` is the target's Relation with its named scopes, typed from the target. One case is circular for TypeScript: a Model's association to itself whose scope calls the Model's own scopes, which needs its field's type written out (`children: HasMany<typeof Category> = hasMany(Category, { scope: (q) => q.top() })`). It's also checked when the scope first runs (`UnknownAttribute`, and `TypeError` if the scope doesn't return a Relation of the target).
- The scope applies to lazy reads and to preloads alike. A `hasMany`'s records come in the scope's order, then by primary key, and a `hasOne` takes the first by the scope's order. Records built or created through the association take the scope's equality values, so `scope: (q) => q.where({ published: true })` creates published posts. `deleteAll()` and `updateAll()` through it only touch the scope's records. A scope using `limit`, `offset` or `distinct` works for lazy reads, but preloading it throws `IncompatibleRelation`, because a grouped preload would apply them to every owner's records together (Rails gives silently wrong results here).
- `dependent:` sets what destroying the owner does to an association's records, as in Rails: `"destroy"`, `"deleteAll"`, `"nullify"`, `"restrictWithException"` or `"restrictWithError"` on a `hasMany`, and the same with `"delete"` in place of `"deleteAll"` on a `hasOne` (its first record, by the scope's order or the primary key). `belongsTo` has none; a strategy the kind doesn't have is a type error and an `InvalidModel`. `"destroyAsync"` waits for a job library (#35).
- Strategies run when a persisted owner is destroyed, after its `beforeDestroy` callbacks and before its DELETE, so an abort leaves the records alone. (Rails runs them where the association is declared among the callbacks, so an abort declared later comes too late.) Restrictions are checked first, so a restricted owner touches nothing:
  - `"restrictWithException"` throws `DeleteRestriction` ("Cannot delete record because of dependent posts") while there are records.
  - `"restrictWithError"` adds a `base` error instead ("Cannot delete record because dependent posts exist", or "…because a dependent profile exists"), so `destroy()` returns `false` and `destroyOrThrow()` throws `RecordNotDestroyed`.
  - `"deleteAll"`, `"delete"` and `"nullify"` are statements sent in one `batch()` with the owner's DELETE, so all of it happens or none of it does. Callbacks on the records don't run, as in Rails.
  - `"destroy"` runs each record's destroy lifecycle, with its callbacks and its own dependents, and its DELETE goes in the same batch as the owner's, so all of it happens or none of it does. Every record's `beforeDestroy` runs before anything is written, and the `afterDestroy` callbacks run afterwards, the records' before the owner's. If a record's destroy aborts, nothing is written and the owner's destroy throws `RecordNotDestroyed`. If a record's own `"restrictWithException"` refuses, its `DeleteRestriction` propagates as it is.
- Without a strategy, destroying an owner whose records point at it leaves the database to decide: D1 enforces foreign keys, so it throws `InvalidForeignKey`. Polymorphic associations, counter caches and inverse inference are out of scope.

## Persistence results

| Method                                   | Resolves to                           | Domain errors                                         |
| ---------------------------------------- | ------------------------------------- | ----------------------------------------------------- |
| `save()` / `update(attrs)`               | `true` / `false`                      | constraint errors, `RecordDestroyed`                  |
| `saveOrThrow()` / `updateOrThrow(attrs)` | `true`                                | same as above, plus `RecordInvalid`, `RecordNotSaved` |
| `create(attrs)`                          | record, persisted or not              | constraint errors                                     |
| `createOrThrow(attrs)`                   | persisted record                      | same as above, plus `RecordInvalid`, `RecordNotSaved` |

| `destroyOrThrow()`                       | destroyed record                      | same as above, plus `RecordNotDestroyed`              |

Any error thrown by a callback other than an `abort(...)` propagates unchanged. That includes an error from an `after*` callback after the persistence lifecycle has already succeeded. Operational D1 errors always propagate. `false` means only "validation failed" or "a callback aborted" (ADR-0005).

## Constraint errors

_Guide:_ [errors](../site/guide/errors.md). _Code:_ `src/constraints.ts`.

- `RecordNotUnique`, `InvalidForeignKey`, `NotNullViolation` and `CheckViolation`, all subclasses of `ConstraintViolation`, are recognized from D1 error messages on insert, update and delete. They carry the original error as `cause`, and `.table`, `.columns` and `.attributes` where the message names them (SQLite's foreign-key and check messages don't name a column). The same errors come from statements and batches. `.table` is the table D1's message names, and `.attributes` are mapped when that table is one being written to (a trigger's write to another table leaves them empty). When the message names no table (foreign-key and check failures), it's the only table written to. A batch that writes to several then has `.table` `null`, and the message starts with `batch:`.
- Both the throwing and non-throwing methods throw them. After a constraint error the caller's own changes are kept and `errors` is not changed, because nothing was persisted. Timestamps are only applied once D1 accepts a write, so a failed save doesn't leave `createdAt`/`updatedAt` behind.
- Uniqueness validation is a friendly early check, not race-safe. The database constraint has the final say.

## Validation

_Guide:_ [validations](../site/guide/validations.md). _Code:_ `src/validations.ts`, `src/lifecycle.ts`.

`await record.isValid()` is the only public entry point. It clears `errors`, runs `beforeValidation`, runs the synchronous and asynchronous validators (uniqueness reads D1), runs `afterValidation`, and returns `true`/`false`. It catches `abort()` and returns `false`; every other error propagates. `save()` and `saveOrThrow()` call it internally. `isChanged()` is a pure synchronous state check, while `isValid()` does work and may query D1.

## Validators

_Guide:_ [validations](../site/guide/validations.md). _Code:_ `src/validations.ts`.

Declared in `static {}` with `this.validates(attribute, rules)`. The attribute name and the `if` callback's record are typed against the Model. Every declared validation runs, in declaration order, with no stopping at the first failure, so one attribute can collect several errors. Within one `validates` call the rules apply in a fixed order: presence, length, format, inclusion, numericality, uniqueness.

All validators accept `allowNull` (skip when the value is null), `message` (replaces every default message from that call) and `if: (record) => boolean`. Without `allowNull`, a null value fails `presence`, `format`, `inclusion` and `numericality`. `length` counts it as length 0 (so it fails a `minimum` or `is`, and passes a `maximum`), and `uniqueness` never treats it as taken.

Default messages (Rails' English): `blank` "can't be blank", `tooShort` "is too short (minimum is N characters)", `tooLong` "is too long (maximum is N characters)", `wrongLength` "is the wrong length (should be N characters)", `invalid` "is invalid", `inclusion` "is not included in the list", `notANumber` "is not a number", `notAnInteger` "must be an integer", `greaterThan`/`greaterThanOrEqualTo`/`lessThan`/`lessThanOrEqualTo` "must be greater than (or equal to) N" / "must be less than (or equal to) N", `taken` "has already been taken".

- `presence`: not null, and not blank after trimming a string. For a boolean, use `inclusion: [true, false]`.
- `length`: `{ minimum, maximum, is }`.
- `format`: `{ with: /re/ }`, or `format: /re/` as shorthand.
- `inclusion`: `{ in: [...] }`, or an array as shorthand.
- `numericality`: `{ onlyInteger, greaterThan, greaterThanOrEqualTo, lessThan, lessThanOrEqualTo }`, or `true`. Only real numbers pass: a numeric string such as `"12"` is `notANumber`, so convert form input first.
- `uniqueness`: `{ scope: [...], caseSensitive }`. It leaves out the record itself when updating and runs `SELECT 1 … LIMIT 1` through the record's Database (so the same session). `null` is never taken, matching SQLite's UNIQUE, which allows any number of NULLs. `caseSensitive: false` compiles to `lower(col) = lower(?)`, and SQLite's `lower()` only lowercases ASCII letters.

## Callback lifecycle

_Guide:_ [callbacks](../site/guide/callbacks.md). _Code:_ `src/lifecycle.ts`, `src/declarations.ts`.

Declared in `static {}`: `this.beforeValidation(fn)`, `afterValidation`, `beforeSave`, `beforeCreate`, `beforeUpdate`, `afterCreate`, `afterUpdate`, `afterSave`, `beforeDestroy`, `afterDestroy`. Each takes a function that receives the record, typed as the Model's record, and may be async; callbacks of one kind run in declaration order. A subclass runs its parent's callbacks and validations plus its own, and declaring on it never changes the parent. Declarations belong in the class's `static {}` block: once a Model has been used (`db.model(X)`), declaring on it throws `InvalidModel`, so request code can never add callbacks that leak into later requests.

```text
beforeValidation → validators → afterValidation
→ beforeSave → beforeCreate | beforeUpdate
→ D1 write (skipped when a persisted record is still clean)
→ record becomes persisted and clean
→ afterCreate | afterUpdate → afterSave
```

- `after*` callbacks run after a **successful persistence lifecycle**, which isn't necessarily a D1 write. Saving a clean persisted record runs every callback, issues no UPDATE and leaves `updatedAt` unchanged, as in Rails. If a `before*` callback changes an attribute, the record is dirty again and the UPDATE happens.
- An `after*` callback that changes the record makes it dirty again, and no second write happens automatically.
- Nothing rolls back after a successful write.

## Abort

_Guide:_ [callbacks](../site/guide/callbacks.md), [persistence](../site/guide/persistence.md). _Code:_ `src/lifecycle.ts`.

```ts
this.beforeSave((account) => {
  if (account.suspended) throw abort("Account is suspended");
});
```

- `abort(reason)` returns a `CallbackAbort` (a `D1RecordError`; the reason defaults to "Aborted by a callback"), and only that class is caught. Returning `false` never halts anything.
- It only takes effect in `beforeValidation`, `afterValidation`, `beforeSave`, `beforeCreate`, `beforeUpdate` and `beforeDestroy`.
- `save()` returns `false`, does no write, and keeps the dirty and new-record state. `saveOrThrow()` throws `RecordNotSaved` with the reason. `destroy()` returns `false`, and `destroyOrThrow()` throws `RecordNotDestroyed`.
- `record.abortReason` holds the reason. It's cleared at the start of each `isValid()`, `save()` and `destroy()`, and never copied into `errors`.
- An `abort()` in `afterSave`, `afterCreate`, `afterUpdate` or `afterDestroy` becomes `AbortAfterPersistence`, which records the callback name, the reason and the original `CallbackAbort` as `cause`. The persisted or destroyed state stays as it is.

## Destroyed records

_Guide:_ [persistence](../site/guide/persistence.md). _Code:_ `src/record-state.ts`, `src/lifecycle.ts`.

- A record is marked destroyed only after the D1 `DELETE` succeeds, and before `afterDestroy` runs. Destroying a never-saved record sends nothing, since there's no row, and marks it destroyed. If `afterDestroy` throws, the row stays deleted and the record stays destroyed.
- `isDestroyed()` is `true` and `isPersisted()` is `false`. Attributes stay readable, but the record is read-only: setting a property or calling `assign` throws `RecordDestroyed`.
- `save`, `saveOrThrow`, `update`, `destroy` and `reload` throw `RecordDestroyed`.
- A keyless record from `select(...).distinct()` has no identity to write by, so the same methods throw `MissingAttribute`. A record constructed directly (`new User()`) has no Database, so they throw `NoDatabase`.

## Relations

_Guide:_ [querying](../site/guide/querying.md). _Code:_ `src/relation.ts`, `src/relation-checks.ts`, `src/load.ts`, `src/query.ts`, `src/compiler.ts`, `src/comparisons.ts`, `src/sql.ts`.

- Every modifier returns a new Relation. Building a Relation never queries D1.
- `static primaryKey` (default `"id"`) must name a declared attribute, or `db.model(X)` throws `InvalidModel`. `find(id)` takes one id, a `string | number`, and resolves to a record. `find(1, 2)` or `find([1, 2])` resolves to an array in the ids' order, or in the Relation's order if it has one, as in Rails. It's one query, repeated ids are found once, `find([])` resolves to `[]`, and a missing id throws `RecordNotFound` saying how many were found. Ids are cast to the key's type first, as in Rails, so `"01"` and `1` are the same id for an integer key. Unlike Rails, `find(1, 1)` still resolves to an array, so the return type follows the arguments. Any number of ids fits in the one query, as with `where`.
- An empty conditions object (`where({})`, `whereNot({})`, `findBy({})`) adds no condition. An `undefined` value throws `TypeError`: use `null` to match NULL, or leave the key out. `undefined` would otherwise bind NULL and silently match nothing.
- Condition values (`where`, `whereNot`, `findBy`, `exists`, lists and comparisons) are cast as assigned values are, except that a finite number matches a `string` attribute as its decimal string (`7` → `"7"`), as `find` does for a text key and as Rails does, so a foreign key of another type still finds its target. One that can't be cast matches nothing (`1 = 0`), as in Rails 6.1+, never NULL and never an error, so `where({ quantity: "abc" })` finds nothing and `find("abc")` on an integer key throws `RecordNotFound`. In a list, the values that can't be cast are left out. So `whereNot` with one matches every row, NULLs included (`NOT (1 = 0)`), as in Rails: excluding a record by a value that can't be cast excludes nothing.
- `where({ x: null })` → `"x" IS NULL`. `where({ x: [1, 2] })` → `"x" IN (SELECT value FROM json_each(?))`, the whole list bound as one JSON value (converted like the attribute's own values), so a list of any length fits D1's 100 bound parameters. `where({ x: [] })` → `1 = 0`. `whereNot({ x: [] })` → `1 = 1`. `where({ x: [1, null] })` → `("x" IN (SELECT value FROM json_each(?)) OR "x" IS NULL)`.
- Comparisons: `where({ age: gte(18) })`, `gt`, `lt`, `lte`, and `where({ createdAt: between(start, end) })`, which includes both ends like Rails' `start..end`. `between(start, end, { excludeEnd: true })` is `start <= x < end`, like `start...end`. `gte` and `lte` are also Rails' endless and beginless ranges. The value is converted like the attribute's own, so dates compare by time, and its type must be the attribute's. Only number, string and datetime attributes can be compared: a comparison on a boolean or `json` attribute is a type error, and throws `TypeError`. A comparison with `null` or `undefined` throws `TypeError`: use `where({ x: null })` to match NULL. Comparisons are values of their own class, so a `json` attribute's object value (`{ gt: 1 }`) still means equality. A record built from the Relation doesn't take a comparison's value.
- `whereNot` wraps the whole condition: `whereNot({ a, b })` → `NOT ("a" = ? AND "b" = ?)`. Following SQL semantics, `whereNot({ role: "admin" })` also excludes NULL roles. `whereNot({ role: null })` → `"role" IS NOT NULL`.
- Other hand-written conditions must be `sql` tagged templates (ADR-0006): ``where(sql`lower(${column("email")}) = ${email}`)``. Plain strings are rejected with a `TypeError` (and are compile errors). Values interpolated into a fragment have no declared type, so a `Date` is bound as ISO text and a boolean as 1/0, matching how attributes are stored.
- `order({ createdAt: "desc", id: "asc" })` sorts by each key in turn, and repeated calls append. NULLs sort as SQLite sorts them (first in ascending order) unless placed: `order({ role: { direction: "asc", nulls: "last" } })` compiles to `NULLS LAST`. An expression is an `sql` fragment: ``order(sql`lower(${column("email")})`)``, with the direction inside it. Plain strings throw `TypeError`. `reorder(spec)` replaces the order so far, as in Rails, and `reorder()` removes it. `limit`/`offset` page, and `offset` works without a `limit`.
- `first()` and `last()` with no order sort by the primary key ascending or descending. With `limit`/`offset`, `first`, `last`, `take` and `exists` work within that page (so `limit(0)` has none). `last()` reverses every direction of an explicit order, and moves placed NULLs to the other end, as Rails' `reverse_order` does. It can't reverse an `sql` fragment, so it throws `IrreversibleOrder` (Rails' `IrreversibleOrderError`). That is stricter than Rails, which flips a plain string order such as `"name DESC"` and only raises for ones it can't parse (function calls, NULLS placement). A fragment is a template with bound values, and reversing it would mean parsing SQL. `take()` adds no ordering.
- `find()`, `findBy()` and `findByOrThrow()` keep the Relation's where conditions, scopes and includes, ignore its limit, offset and `select()`, and always load full rows. They ignore its order too, except that `find` with several ids returns them in the Relation's order when it has one (see above).
- `or()`: same Model on the same database (checked when the query runs, #93), and the same select, order (fragments compare by text and values), limit, offset and distinct. Only where conditions may differ, and each side is wrapped in parentheses. Otherwise it throws `IncompatibleRelation`.
- `merge()`: same Model on the same database only (checked when the query runs, #93). Where conditions combine with AND. For order, limit, offset, select and distinct, a clause the argument sets explicitly replaces the receiver's, and a clause it doesn't set leaves the receiver's alone. Orders are replaced, not concatenated, which is a deliberate difference from Rails. An argument built with `reorder()` replaces the order even when its own is empty, as in Rails. Merging across Models throws `IncompatibleRelation`.
- `toSql()` (#46), as Rails' `to_sql`, returns `{ sql, params }` for the SELECT `toArray()` sends, without sending it, so it needs no database. It shows the columns really loaded (a `select` plus the primary key and the keys `includes` needs), `limit` and `offset` as bound values, and a `none()` Relation as its conditions with `1 = 0`. It isn't the query `count()`, `pluck()` or `exists()` send, as in Rails. Values are never inlined (ADR-0006), so Rails' inlined values are `params` here. The params are the values D1 would bind, filtered attributes included: `onQuery` hides them, `toSql()` doesn't, as Rails' `to_sql` doesn't filter. A Model has it as a static (`User.toSql()`).

## Terminal operations

_Guide:_ [querying](../site/guide/querying.md). _Code:_ `src/relation.ts`, `src/load.ts`, `src/pagination.ts`.

- `toArray`, `first`, `last`, `take`, `find`, `findBy`, `findByOrThrow`.
- `pluck("email")` resolves to converted values. `pluck("id", "email")` resolves to tuples.
- `count()` counts over the whole query as a subquery, so it always equals the number of rows `toArray()` would return, including `limit`, `offset`, `select` and `distinct` (with `select("role").distinct()`, NULL counts as one distinct value). `count("role")` counts non-null values, and after `distinct()` it compiles to `COUNT(DISTINCT "role")`, the distinct non-null values.
- `exists(conds?)` issues `SELECT 1 … LIMIT 1`.
- `paginate({ page, perPage })` (#100) resolves to a **Page**, a plain object ready for `Response.json()`: `{ records, page, perPage, total, totalPages, hasNext, hasPrevious }`. Its `COUNT` (as `count()`'s, so `select` and `distinct` count what the pages hold) and the page's `SELECT` go to D1 as one batch: one round trip. `includes()` preloads follow, as for `toArray()`. It's a terminal, not chainable (`page(2).per(25)`), since only a terminal can promise one round trip. Pages end their order with the primary key (alone, with no order, as `first()` does), unless the order already has it, so tied records keep their pages between requests; after `distinct()`, where the key isn't loaded, they end it with the selected attributes instead. `totalPages` is `ceil(total / perPage)`, so `0` with no records, as in Kaminari; `hasNext` is `page < totalPages`, and `hasPrevious` is `page > 1`. Past the last page, `records` is `[]` with the real `total`, not an error.
  - `{ count: false }` skips the `COUNT`, which reads every matching row (D1 bills rows read): one `SELECT` fetches `perPage + 1` records, returns `perPage` of them, and reports `hasNext`. Its type has no `total` or `totalPages`, rather than `undefined` ones. Keyset (cursor) pagination is a separate, deferred issue.
  - `page` and `perPage` are untrusted input, cast as an `integer` attribute's assigned value is (#81): `"2"` is 2, and `"abc"`, `1.5` or anything below 1 rejects with `TypeError`, before any query, as does a page so far that its offset isn't a safe integer. `undefined`, `null` and `""` mean the default, so `paginate({ page: url.searchParams.get("page") })` is page 1 without one. The default `perPage` is `static perPage` (25), and a larger `perPage`, given or declared, is capped at `static maxPerPage` (100) without an error. Both are inherited, usually set on the app's base class, and each must be a whole number from 1, or the Model is an `InvalidModel` when it's first used. D1 caps neither rows returned nor response size; the cap exists because D1 bills every row read, a Worker has 128 MB of memory, and a query has 30 seconds.
  - A Relation with its own `limit` or `offset` rejects with `IncompatibleRelation`, rather than having them replaced. On `none()`, it's an empty page (`total: 0`) with no query. On a `hasMany`, it queries D1 even when the owner has the records loaded, as `count()` does.
- `size()`, `isEmpty()` and `hasAny()`, as Rails' `size`, `empty?` and `any?`. A loaded association answers from its records, built ones included, without a query. Otherwise `size()` is a `COUNT(*)` plus an association's unsaved built records, and `isEmpty()` is `!exists()` (it's `false` without a query while an association has unsaved built records). `hasAny()` is the opposite of `isEmpty()`. Rails' `one?`, `many?` and `none?` aren't offered: `hasOne`/`hasMany` would read like the association declarations, and `isEmpty()` already says "none".
- Naming: `is…` asks about a state of the thing itself (`isNewRecord()`, `isEmpty()`, `isLoaded()`, `isAttributeChanged()`), and `has…` about something it holds: a collection's records (`hasAny()`) or a record's last saved change (`hasSavedChangeTo()`). Methods that raise end in `OrThrow` (ADR-0005).
- `none()` never touches D1, so it needs no database (no `withDatabase` or binding): `toArray` gives `[]`, `count` gives `0`, `exists` gives `false`, `first`/`last`/`take`/`findBy` give `null`, `pluck` gives `[]`, and `find` throws `RecordNotFound`. Chaining keeps it `none()`. `none().or(r)` and `r.or(none())` both return `r`.

## Partial records

_Guide:_ [querying](../site/guide/querying.md). _Code:_ `src/relation.ts`, `src/record-state.ts`.

- `select()` on a Model Relation accepts only declared attributes. The primary key is always loaded too, so a partial record keeps its identity, except after `distinct()`, where adding the key would make every row distinct. Such records carry only the selected attributes.
- Reading an unloaded attribute throws `MissingAttribute`, including when a validator or callback reads it. Setting one is allowed and makes it loaded and dirty.
- `save()` writes only changed attributes (plus `updatedAt`), and never fills in unloaded ones. `reload()` loads the full row.

## Batches

_Guide:_ [batches](../site/guide/batches.md). _Code:_ `src/statement.ts`, `src/record-statement.ts`, `src/unit-of-work.ts`, `src/database.ts`, `src/relation.ts`, `src/load.ts`.

```ts
const userId = crypto.randomUUID(); // ids generated in code link rows inside one batch
await db.batch([
  db.model(User).toInsert({ id: userId, email: "a@example.com" }),
  db.model(Post).toInsert({ userId, title: "Hello" }),
  db.model(Post).where({ published: false }).toDeleteAll(),
]);
const published = await db.model(Post).where({ id: postId }).updateAll({ published: true }); // 1
await db.model(Post).updateAll(sql`${column("views")} = ${column("views")} + ${1}`);
```

- Bulk writes run when called, skipping validations, callbacks and hydration, as Rails' `insert_all`/`update_all`/`delete_all` do: `insert(attrs)`, `insertAll(rows)`, `upsert(attrs)` and `upsertAll(rows)` resolve to D1's `meta` (`changes`, `last_row_id`, `duration`, …); `updateAll(changes)` and `deleteAll()` resolve to the number of rows, as in Rails. Unknown attributes, `undefined` values and plain strings reject the call.
- A **Statement** is the same write prepared for a batch, from the `to…` forms: `toInsert`, `toInsertAll`, `toUpsert`, `toUpsertAll`, `toUpdateAll`, `toDeleteAll`, as records have `toSave()`/`toDestroy()`. It's compiled when built (so unknown attributes and the like throw then), runs on the Database it was built from, and only runs with its batch.
- A Statement has `toSql()` (#46): the `{ sql, params }` its batch sends, as compiled when it was built, with the same real values as a Relation's. A record statement (`toSave()`, `toDestroy()`) has none: its SQL depends on validations and callbacks that run inside the batch. Its `toSql()` is `@internal`, so TypeScript rejects the call, and in JavaScript it throws a `TypeError` saying why.
- `db.batch([...])` runs statements atomically with D1's `batch()`: all of them are written, or none. It resolves to each entry's result, in order: a statement's `meta`, or a record statement's record. `[]` resolves to `[]` without a query. A statement or record from another Database rejects with `IncompatibleRelation`, before any callback runs.
- Records join a batch through **record statements**: `db.batch([user.toSave(), post.toDestroy(), db.model(Log).toInsert({…})])`. Unlike statements, their validations and callbacks run, when the batch runs:
  1. Each record, in order, runs its validation and before-callbacks, exactly as `save()` or `destroy()` would (a destroy brings in its `dependent:` strategies). The first that's invalid or aborts throws `RecordInvalid` (with `.record`), `RecordNotSaved` or `RecordNotDestroyed`, as saving with `save!` inside a Rails transaction does, and nothing is sent.
  2. Every write goes out as one atomic batch. If D1 refuses it (a constraint error, thrown as usual), nothing is written and every record keeps its unsaved state.
  3. Each record takes its saved state (loading what `RETURNING` gave back, or becoming destroyed), then its after-callbacks run, in order.
     This differs from a Rails transaction, where one record's `after_save` runs before the next record's `before_save`: here every before-callback runs before any write, much like Rails' `after_commit`.
- Records in one batch can't point at each other's database-generated keys, which don't exist until the batch is written. Keys generated in code (`generateId`, or a `default`) exist from `build()`, so records can be linked by them, or through autosave (#29).
- There's no interactive `transaction(async tx => …)`. D1 can't hold a transaction open across awaits, so a callback that reads and then decides what to write can't be made atomic; a batch of statements and record statements prepared beforehand can.
- `insert(attrs)` writes one row. Declared attribute defaults fill attributes that aren't given (unlike Rails' `insert_all`, because in D1 app-side defaults are where keys are generated), and `createdAt`/`updatedAt` are set unless given, as Rails does. A Relation's equality conditions are inserted too, as with `build()`. A constraint failure throws, as everywhere (ADR-0005).
- `insertAll(rows)` inserts several rows in one statement (Rails' `insert_all!`), and throws on a duplicate, writing nothing. Every row must be given the same attributes, in any order, compared as given, before defaults and timestamps are filled in (`TypeError` otherwise, and for `[]`), and defaults, timestamps and a Relation's equality values apply to each row. The rows are bound as one JSON value (`INSERT … SELECT … FROM json_each(?)`), so any number of rows fits in one statement, within D1's 100 bound parameters and its 2 MB limit on one value. Rows with no attributes at all can't be inserted together or with an `onDuplicate` or upsert (`TypeError`, as Rails raises); a lone `insert({})` writes the table's `DEFAULT VALUES`.
- `insert(attrs, { onDuplicate: "skip" })` and `insertAll(rows, { onDuplicate: "skip" })` skip rows that clash with a unique index (`ON CONFLICT DO NOTHING`). Skipping is opt-in: Rails' `insert` and `insert_all` skip by default, which ADR-0005 rules out.
- `upsert(attrs)` and `upsertAll(rows)` update a row that clashes with the unique index on `uniqueBy`, which is the primary key by default or names another unique index's attributes. As in Rails, only the attributes given are updated, never ones filled in by defaults (such as a generated key), and not the `uniqueBy` ones or `createdAt`; `updatedAt` is set. Rails' `returning` and `update_only` options are deferred (#36).
- `updateAll(changes)` takes an object of declared attributes (converted like any write) or an `sql` fragment, and leaves `updatedAt` alone, as in Rails. `{}` is a `TypeError`: `updateAll` rejects with it, and `toUpdateAll` throws it.
- Which rows `updateAll`/`deleteAll` write follows Rails. With a `limit` or `offset`, it's `WHERE <primary key> IN (SELECT <primary key> … ORDER BY … LIMIT … OFFSET …)`, so the Relation's order picks the rows. Otherwise it's the Relation's conditions, and `order`, `select` and `includes` don't matter. `distinct()` is `IncompatibleRelation`: `updateAll`/`deleteAll` reject with it, and their `to…` forms throw it.
- On a `none()` Relation, `updateAll`/`deleteAll` send nothing and resolve to `0`, as in Rails. Its `to…` statements are still sent with their batch, as `WHERE 1 = 0`, and report `changes: 0`.
- Neither Relations nor statements are awaitable directly (they have no `then`), so an `async` function that returns one never runs it by accident. A write runs only when its method is called, or when its statement's batch runs.

## Instrumentation

_Guide:_ [logging](../site/guide/logging.md). _Code:_ `src/executor.ts`, `src/filtering.ts`.

- `connect(env.DB, { onQuery(event) })` is called once per statement, batches included, with `{ model, sql, params, durationMs, meta, error? }` (`model` is the statement's Model's class name). The integration tests' query-count checks use this same hook. No logger is built in.
- **App-wide (#78):** `static onQuery` on a Model class, usually the app's base class (`static override onQuery: QueryListener = (event) => …`), is called with the same event for every statement of that Model and those extending it, at every level (the binding, `withDatabase`, an explicit `db`), after the database's own `onQuery`. It's inherited, and a Model's own replaces it. It holds no request state, so it's safe on a class, and can't tell requests apart: a request's ID comes from a database opened for it with `withDatabase`.
- **Filtered attributes (#83):** `static filterAttributes: readonly (string | RegExp)[]`, as Rails' `filter_attributes`, starts on `Model.Base` as Rails' default `filter_parameters` (`passw`, `email`, `secret`, `token`, `_key`, `crypt`, `salt`, `certificate`, `otp`, `ssn`, `cvv`, `cvc`). An attribute is filtered when its snake_case name holds a string entry, in any case (`passwordDigest` → `password_digest` holds `passw`; `apiKey` → `api_key` holds `_key`), or a RegExp entry matches the attribute or its snake_case name. It's inherited, and a Model or the app's base class replaces it (`static override filterAttributes = [...Model.Base.filterAttributes, "iban"]`; `[]` filters nothing). A filtered attribute's bound values are `"[FILTERED]"` in `event.params`: inserts, updates, `updateAll`, conditions, lists (the whole list, bound as one value), comparisons, and a record's stored primary key in its `UPDATE` and `DELETE`; in a multi-row insert's single JSON value, its column is `"[FILTERED]"` in every row. D1 still gets the real values. Values in `sql` fragments have no attribute, so they're shown as given. A cast error (#81) shows a filtered attribute's value as `[FILTERED]`, and `RecordNotFound` (from `find`, `find([...])` and `reload`) shows a filtered primary key's values as `[FILTERED]`. `toJSON()` and `attributes()` are unchanged, as in Rails.
- **A listener never changes a query's outcome:** each is called on its own, and one that throws is logged with `console.error` ("onQuery threw; the query's result is unaffected:"), so the query's result, or D1's (translated) error, reaches the caller as it would have, and the other listener and the other statements of a batch are still reported. `event.model` is the Model's class name: `""` for an anonymous class, and renamed by a bundler that renames classes (Wrangler keeps names by default).
- In a batch, each statement's `durationMs` is D1's own timing for it (`meta.duration`). When a batch fails, D1 doesn't say which statement failed, so every statement is reported with the error and the batch's elapsed time. `event.error` is D1's own error; the caller gets the translated `ConstraintViolation`, with D1's error as its `cause`.

## Errors

_Guide:_ [errors](../site/guide/errors.md). _Code:_ `src/errors.ts`.

Everything extends `D1RecordError`:

- **Lifecycle:** `RecordNotFound`, `RecordInvalid` (`.record`), `RecordNotSaved`, `RecordNotDestroyed`, `RecordDestroyed`, `CallbackAbort` (from `abort()`), `AbortAfterPersistence` (`.callback`, `.reason`)
- **Usage:** `UnknownAssociation`, `InvalidModel` (a problem in a Model's declaration, detected the first time it's used), `UnknownAttribute`, `MissingAttribute`, `IncompatibleRelation`, `IrreversibleOrder`, `DeleteRestriction`, `AssociationNotLoaded`, `NoDatabase`, `NoSession`
- **Names are a Model's own (#84).** Attributes and associations are looked up in Maps, so a name every object inherits (`constructor`, `__proto__`, `toString`, `hasOwnProperty`), from a URL's `?include=` or a JSON key say, is an `UnknownAttribute` or `UnknownAssociation` like any other unknown name, from every method that takes one. Reading an unknown attribute is `UnknownAttribute`; `MissingAttribute` is only for a declared attribute that `select` didn't load.
- **Constraints:** `ConstraintViolation`, with subclasses `RecordNotUnique`, `InvalidForeignKey`, `NotNullViolation` and `CheckViolation`
